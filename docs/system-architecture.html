Meeting Notes: System Architecture

Upload a client meeting recording, get back a speaker-labelled transcript, summary, action items, decisions, scope-change flags and a commitment log. App and worker on Railway, speech and LLM via NVIDIA hosted APIs, speaker diarization run on CPU in our own worker.

Volume assumption: 2 meetings/day, ~1.5 hrs each, ~66 hrs audio/month. V1 draft, 26 Oct 2026.

2. Components

Railway

Web app

  • Next.js, UI and API routes in one service
  • Login, roles: admin, member
  • Issues presigned R2 upload URLs, never handles the file itself
  • Transcript view synced to audio playback
  • Export: docx, PDF, markdown
Railway

Postgres

  • All text, metadata and job state
  • Jobs table is the queue, claimed with FOR UPDATE SKIP LOCKED
  • Full-text search on segments
  • Small: years of transcripts fit in a few GB
Railway

Worker

  • Python, runs as a cron service, exits when queue is empty
  • ffmpeg + pyannote on CPU, ~2-3 GB RAM while running
  • Each stage saves before the next starts, so a crash resumes mid-pipeline
  • Provider adapter wraps ASR and LLM calls
Cloudflare

R2 bucket

  • Audio only, private, no public URLs
  • Needed because a Railway volume attaches to one service, and both app and worker need the file
  • Upload extracted audio, not video, to stay inside free 10 GB
  • Lifecycle rule deletes audio after retention period
NVIDIA

Speech to text

  • Hosted Parakeet 1.1b RNNT multilingual, handles Hindi and English
  • Called per diarized chunk, so each piece of text already has a speaker
  • Language per meeting, default multi (auto detect)
NVIDIA

LLM

  • Receives transcript text, never audio
  • Nemotron 3 Super, 1M context: whole transcript in one call, no chunking
  • Second call for scope changes, only when the project has a baseline
  • Structured JSON out, every finding cites segment IDs

3. Pipeline per meeting

  1. UploadBrowser + web app. User picks client, project and meeting type, ticks consent. If the file is video, the browser uploads it and the worker extracts audio first. Meeting row created, job status queued.
  2. ClaimWorker. Cron wakes, claims the oldest queued job, sets preprocessing.
  3. PreprocessWorker, ffmpeg. Download from R2, convert to 16 kHz mono wav, normalise loudness. If source was video, replace it in R2 with the audio file.
  4. DiarizeWorker, pyannote on CPU. Produces speaker turns: who spoke from when to when. ~10-15 min per hour of audio. Saved as segments with empty text.
  5. TranscribeWorker to NVIDIA ASR. Each speaker turn (long turns split at ~30 s) sent to Parakeet. Text written back into its segment. Failed chunks retried 3 times, then the job goes to needs_attention.
  6. AnalyseWorker to NVIDIA LLM. Template chosen by meeting type. Whole transcript in one call, then a scope-change call if a baseline exists. Outputs: summary, decisions, action items with owner and due date, open questions, scope-change flags, commitments. Each item stores the segment IDs it came from.
  7. ReadyWorker. Job set ready, temp files deleted. App shows it in the meeting list. User renames speakers, edits text, exports.

Job states

queued→ preprocessing→ diarizing→ transcribing→ analysing→ ready | needs_attention failed

5. Rules built into the design

No silent fallback

If NVIDIA fails, the job waits in needs_attention. It never reroutes to another provider on its own.

Audio goes one place

Only the ASR endpoint receives audio. The LLM gets text only.

Original is never overwritten

Edits go to edited_text. Raw ASR output stays for audit.

Evidence or it did not happen

Every action, decision, scope flag and commitment links to the segments it came from.

Retention

Audio auto-deleted from R2 after a set period. Text kept unless a meeting is deleted.

Consent recorded

Upload requires the consent flag. Stored on the meeting.
